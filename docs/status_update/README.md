# Status update, 13 October 2026

Figures for the team channel, generated by `python3 sim2/make_status_update.py` from the result files in `figures/` (every number below is read from those files).

## Post

**What the project is about.** Hospitals use AI models that flag patients at risk, for example of sepsis. When a flag works, clinicians treat the patient and the bad outcome often doesn't happen. The model's prediction then looks wrong, so its measured accuracy changes even though nothing is broken. Monitoring tools try to explain such changes, and we show they blame the wrong cause: they read the alert's success as a change in patients' underlying risk. Our method gets the cause right by holding the alert back for a randomly chosen group of patients and comparing.

**Where we are.** All the simulation experiments are done, and every result can be regenerated with one command. The one missing piece is a run on MIMIC-IV, a large set of real hospital records. Someone with approved PhysioNet access needs to run `sim2/run_e6.sh all <username>` on their own computer, since the data can't be shared. It downloads about 3 GB, the main run takes 20 to 40 minutes, and it saves only summary numbers. Figures below, one caption each.

How the work flows, from data to paper. Green is done, half yellow is partly done, red is missing. All the simulation work is done. **02. Standard monitoring blames the wrong cause** (`02_attribution.png`)

In a simulated hospital we know exactly what changed. On the left, the only change is that clinicians act on the alerts. That alone changes the model's prediction error, because treated patients no longer have the outcomes the model predicted for them. Standard monitoring can't see the alert, so it blames a change in patients' underlying risk. Our method holds the alert back for a random group of patients, compares, and correctly blames the alert. On the right, several things change at once, and our method still gets each part right.

**03. More data doesn't fix it** (`03_more_data.png`)

The usual correction uses treatment records to work out what the alert itself did. It fails when, before the alert existed, patients like the ones it now flags were never treated. It then gets even the direction wrong: it says the alert lowered prediction error (−0.009) when it raised it (+0.027). With 20 times more patients its error bars shrink, but around the wrong answer. Our method gets it right (+0.027).

**04. Retraining backfires** (`04_retraining.png`)

When accuracy changes, a common response is to retrain the model on recent data. But the flagged patients were treated and did fine, so the retrained model learns that they are low risk and stops flagging them. The benefit then collapses every other round (11.5 → 0.0 → 7.7 → 0.1 bad outcomes prevented per 100 patients), and the accuracy score looks best in exactly the rounds where the alert helps no one. Retraining only on untreated patients, with a statistical correction, keeps the benefit.

**05. Knowing the cause tells you when to retrain** (`05_refit_rules.png`)

After monitoring for a while, should the hospital keep the model or retrain it? We scored each decision rule by the extra bad outcomes it causes compared with the better choice. Retraining only when our method says the underlying risk changed caused none in any of the four situations we tested. The same rule using standard monitoring causes up to 11.5 extra bad outcomes per 100 patients, about as many as always retraining, because it mistakes the alert's effect for a change in risk.

**06. A drop in accuracy can mean the alert is working** (`06_auroc_vs_benefit.png`)

The more often clinicians act on alerts, the more bad outcomes are prevented (from 1.4 to 12.2 per 100 patients) and the lower the model's measured accuracy (AUROC from 0.73 to 0.64). So a falling accuracy score after launch is not, on its own, a sign that something is wrong.

**07. When the outcome is uncommon, a working alert looks like an improvement** (`07_prevalence.png`)

If the bad outcome is common (40% of patients), a working alert makes prediction error go up, which looks like the model getting worse. At rates closer to real hospital wards (14% and 7%), error goes down instead, which looks like patients getting healthier. Either way, standard monitoring blames a change in risk. Open decision for the team: the paper's introduction currently assumes performance drops after launch.

**08. The same mistake on real patient data** (`08_real_covariates.png`)

We repeated the test on real ICU patients from two hospitals (a public sepsis dataset), simulating only the alert and its effect. Here the alert lowers prediction error at both hospitals. Standard monitoring credits that to lower underlying risk; our method correctly credits the alert. This stands in for the MIMIC-IV run until that is done.
